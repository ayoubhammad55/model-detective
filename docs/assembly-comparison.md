# Assembly Comparison: x86-64 vs AArch64

## 1. Objective

This experiment investigates how a C implementation of logistic regression inference is translated into assembly for two processor architectures: x86-64 and AArch64 (ARM64).

The experiment compares compiler-generated assembly at two optimization levels, `-O0` and `-O2`, to understand how the target architecture and compiler optimization affect the generated instructions.

The objective is to understand the generated code, not to claim that one architecture is faster than the other.

## 2. Compiler Toolchains

### Native x86-64

- Compiler: GCC 13.2.0 (MinGW-w64)
- Target: `x86_64-w64-mingw32`
- Host operating system: Windows

### AArch64 cross-compiler

- Toolchain: Arm GNU Toolchain 15.3.1
- Target: `aarch64-none-linux-gnu`
- Host operating system: Windows

The AArch64 assembly is generated by cross-compiling the same C source file. Physical ARM hardware is not required to generate these listings.

The two targets use different instruction sets and operating-system environments. Consequently, their assembly listings should not be treated as a direct performance comparison.

## 3. Generated Assembly Files

The assembly listings are stored in the `results/` directory.

| File | Architecture | Optimization |
|---|---|---|
| `results/inference_O0.s` | x86-64 | `-O0` |
| `results/inference_O2.s` | x86-64 | `-O2` |
| `results/inference_ARM_O0.s` | AArch64 | `-O0` |
| `results/inference_ARM_O2.s` | AArch64 | `-O2` |

The compiler's `-S` option generates assembly output without linking an executable.

## 4. Reproducing Assembly Generation

### x86-64

Run these commands from the repository root in PowerShell:

```powershell
gcc -S -O0 c\inference.c -o results\inference_O0.s
gcc -S -O2 c\inference.c -o results\inference_O2.s
```

### AArch64

Set the path to the installed cross-compiler:

```powershell
$armgcc = "C:\Program Files\Arm\GNU Toolchain mingw-w64-x86_64-aarch64-none-linux-gnu\bin\aarch64-none-linux-gnu-gcc.exe"

& $armgcc -S -O0 c\inference.c -o results\inference_ARM_O0.s
& $armgcc -S -O2 c\inference.c -o results\inference_ARM_O2.s
```

These commands regenerate the four assembly listings. The actual compiler version and target should be checked if the toolchain is changed.

## 5. Instruction Comparison

### x86-64

The generated x86-64 assembly contains instructions such as:

- `movsd`: moves scalar double-precision floating-point data.
- `mulsd`: multiplies scalar double-precision floating-point values.
- `addsd`: adds scalar double-precision floating-point values.

The exact instruction sequence depends on the compiler version, optimization level, and surrounding code.

### AArch64

The generated AArch64 assembly contains instructions such as:

- `ldr` and `str`: load and store data.
- `fmul`: multiply floating-point values.
- `fadd`: add floating-point values.
- `fdiv`: divide floating-point values.
- `fcmpe`: compare floating-point values and update condition flags.

The optimized AArch64 listing also contains `fmadd`, which performs a fused multiply-add operation.

These are examples from the generated listings. They are not a complete inventory of every instruction used at both optimization levels.

### Shared inference operations

Both implementations carry out the same high-level inference procedure:

1. Read the model parameters and input features.
2. Calculate the linear score.
3. Apply the sigmoid function using the `exp()` library function.
4. Apply the classification threshold.
5. Print the prediction results.

The generated instructions differ because the architectures have different instruction sets, calling conventions, and target environments.

## 6. Effect of Compiler Optimization

### `-O0`

The `-O0` optimization level disables most compiler optimizations. It is useful as a baseline for studying how source-level operations appear in generated assembly.

It does not guarantee a one-to-one correspondence between C statements and assembly instructions.

### `-O2`

The `-O2` optimization level enables a collection of compiler optimizations intended to improve generated code.

Possible changes include simplifying expressions, removing unnecessary operations, improving register usage, and combining arithmetic operations where appropriate.

The exact transformations depend on the source code, compiler version, target architecture, and compiler options.

### Fused multiply-add

The optimized AArch64 listing contains an `fmadd` instruction, which computes a multiplication and addition as one fused operation.

Fused multiply-add can reduce the number of separate arithmetic instructions and rounds the combined result differently from separate multiplication and addition. Therefore, mathematically equivalent calculations may differ slightly in their floating-point results.

The presence of `fmadd` alone does not establish that the entire program executes faster.

### The sigmoid calculation

The inference implementation uses `exp()` to calculate the sigmoid probability.

This operation is provided through a mathematical library rather than being represented by one general-purpose AArch64 instruction. The generated code can include a function call and additional instructions to handle the calculation.

Consequently, inspecting the arithmetic instructions alone does not describe the cost of the entire inference program.

## 7. Assembly Inspection

To inspect the generated files in PowerShell, run:

```powershell
Get-Content results\inference_O0.s
Get-Content results\inference_O2.s
Get-Content results\inference_ARM_O0.s
Get-Content results\inference_ARM_O2.s
```

To locate selected instructions in the AArch64 listings:

```powershell
Select-String -Path results\inference_ARM_O0.s,results\inference_ARM_O2.s -Pattern "fmul|fadd|fmadd|fdiv|fcmpe"
```

These commands help identify relevant instructions in the generated files. The examples described in this document are based on the recorded assembly inspection.

## 8. Numerical Validation

Floating-point calculations can differ slightly between compiled implementations because of rounding behavior, fused operations, and mathematical library implementations.

The project includes automated tests comparing C inference against Python reference calculations for **66 inputs**:

- 60 held-out test samples.
- 6 additional edge inputs, including zero-valued inputs, positive and negative values, and a decision-boundary case.

The tests check numerical agreement within a tolerance of `1e-9` and verify that predicted classes match. The recorded test run passed both test methods.

This provides evidence of numerical consistency for the tested inputs. It does not prove equivalence for every possible input or establish real-world predictive performance.

## 9. Limitations

- Assembly listings show generated instructions, not measured execution performance.
- The x86-64 and AArch64 targets use different instruction sets and operating-system environments.
- Instruction count and assembly file size alone do not establish speed or energy efficiency.
- The ARM64 executable has been tested under QEMU user-mode emulation, not on physical ARM hardware.
- Native ARM latency, throughput, and energy consumption have not been measured.
- The classifier uses synthetic data and one fixed train/test split.
- Numerical validation covers the documented test inputs rather than an exhaustive input space.

## 10. Conclusion

This experiment demonstrates how a trained model's inference calculations can be implemented in C and translated into architecture-specific assembly.

The generated x86-64 and AArch64 listings illustrate how target architecture and compiler optimization affect floating-point instruction sequences, including the use of fused multiply-add instructions in the optimized AArch64 output.

The project also validates Python and C inference across 66 inputs and demonstrates successful execution of a cross-compiled ARM64 binary under QEMU user-mode emulation.

Together, these results provide a practical example of the relationship between machine learning inference, low-level implementation, compiler optimization, and processor architecture, while distinguishing observed behavior from unmeasured performance claims.
